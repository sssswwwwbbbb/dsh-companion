# DSH 整套皮肤开发

把一套皮肤作为统一体验设计，先讨论范围，再确定方案、素材、开发和验收。首次使用应阅读 [项目上下文](references/project.md)，重新核对当前代码与报告。

本技能是可迭代的流程骨架。候选模块不是已确认需求；第一套皮肤的产品范围尚待用户讨论。用户只要求讨论时，先产出范围和功能清单，不直接实现皮肤。

## 先确定产品边界

使用 [皮肤需求模板](assets/skin-brief.md) 记录讨论。先明确三个问题：

1. 皮肤覆盖哪些地方：DSH 主界面、开场、桌宠，还是其中一部分？
2. 哪些是外观变化，哪些会增加行为、交互或其他功能？
3. 首套角色与风格、用户使用场景、可提供的素材是什么？

把每个候选项标为「首版 / 后续 / 不做 / 待定」，并给首版项写可观察的验收标准。保留未定项，不代替用户决定角色、版权许可、交互功能或商业范围。将已确认决定、候选想法和技术限制分开记录。

## 从范围到交付

按当前阶段读取 [开发与验收流程](references/workflow.md)，不一次性执行全部阶段。

- **需求与能力核对**：清单先行，查目标 DSH 版本的真实扩展接口，区分已有、需扩展和未验证能力。
- **视觉与体验方案**：先用少量关键界面与状态验证统一风格，形成素材清单和交互规则；缺失的关键选择在这里讨论。
- **素材准备**：优先复用已有组件、开源素材和用户私有素材，逐项保留来源及许可，不因“公开可下载”就当作允许再分发。
- **配置与实现**：共用现有插件、桌面宿主、授权和配置能力。先实现首套所需的最小配置合同，再连接 UI、动画和桌宠。保持平台及 DSH 版本适配边界。
- **验收与交付**：验证主题切换、各开关、停用/启用、入口恢复、数据保留、异常回退及完整安装激活流程；按本次授权范围交付本地包、发布或部署结果。

## 本项目的约束

- 用户感知入口在 DSH 插件；授权统一，配置切换要能关联选定的各个皮肤模块。
- V1 先用 Mac Apple 芯片验证；Windows 和其他 DSH 版本另行适配，不能沿用 Mac 测试结论。
- 桌宠可以出现在系统桌面；自主行为优先由现有本地状态机承担，不为换皮逐帧调用模型。
- 简洁的业务名称。开关可显示「启用 / 停用」，旁边明确是插件、启动入口还是某项效果，不能混用状态。
- 通过官方扩展接口适配。不要把某版 DSH 的 DOM 选择器或私有实现当作长期有效接口；存在依赖时集中在版本适配层并记录证据。
- 现有配置包仅覆盖动画、桌宠与部分行为设置。DSH 全局主题等仍需能力审查与配置扩展，不能把设计图当作已实现能力。
- 保留激活码、签名密钥、管理员凭据和设备授权的私密性。皮肤资源及配置不要携带可执行代码、任意本地文件读取或未确认的外部请求。
- 构建、发布、服务器部署、真实客户端验收分别报告。遵守当前对话的授权范围，本技能不扩展外部操作权限，也不额外引入审批步骤。
