## 必须修复的发现

### F1｜P1：独立停止请求不能使在途原生激活失效

源码：[原生皮肤运行层](../runtime-src/skin.mjs) L35、L37、L42；[原生主进程](../runtime-src/main.mjs) L155。

复现：开始加载桌宠，媒体尚未就绪时调用原生 `requestStop()`，随后媒体就绪。停止立即把 `visible` 置为 false，但没有取消原来的激活；原激活最终仍返回 `ready:true`，又把 `visible` 置为 true，同时 `mediaPaused` 仍为 true。

该结果在隔离状态机中实际复现，不是点击真实托盘的实机证据。主进程 `/skin/apply` 在激活返回后会根据可见状态调用显示窗口，因此此状态漏洞具备实际重现桌面效果的路径。

最小修正要求：独立停止立即使旧激活不能再成功；每次就绪/显现前检查有效操作及停止约束。Host 尚未消费停止请求时，旧请求及回滚也不能解除抑制；后续只允许按既定主动恢复规则重新开启。修复时需保持 Host/原生代次兼容，不能仅推进原生代次造成下一次正常应用失败。

复验：在媒体加载多个阶段发出独立停止，旧激活不得成功或显现；同时验证 Host 延迟/暂不可用、请求消费一次、主动恢复成功以及正常加载路径。

### F2｜P1：换肤中页面重新握手会把已成功的新选择切回旧皮肤

源码：[插件皮肤服务](../packages/dsh-companion/src/skins.mjs) L25、L27；[协调器](../packages/dsh-skin-core/src/coordinator.mjs) L90。

复现：A 已稳定，开始切换 B 并等待原生就绪；旧页面心跳过期后，新页面握手。`poll()` 无条件调用 `restore()`，此时最后提交的选择仍是 A，于是排入恢复 A。B 先返回成功，随后队列中的恢复又把最终选择和页面改回 A。

本轮实际结果：显式请求回执为 `sample-b`，最终持久/运行选择为 `sample-a`，桌宠被清理。复现使用真实皮肤服务与协调器、受控适配器，不使用用户客户端。

最小修正要求：重新握手加入当前有效操作，或仅在没有待处理的显式选择且恢复目标仍有效时发起恢复。不能把“最后已提交 A”误当成“当前仍希望应用 A”。显式换肤进行中不能另排旧选择覆盖它。

复验：在准备、应用、原生等待及提交前后重载/重连页面，最终选择与最后有效的用户请求一致，回执和实际状态一致，停止意图仍优先。

### F3｜P2：忙碌时停止按钮被禁用，通用请求锁也会吞掉停止请求

源码：[客户端模板](../packages/dsh-companion/src/client.template.js) L33、L34、L72。

静态核对结果：`停止全部皮肤效果` 使用 `disabled:busy`；其请求又经过 `work()` 的 `inFlight.current` 提前返回。因此普通换肤/配置未完成时，用户无法通过该入口触发核心已有的停止优先处理。仅把按钮启用还不足以修复。

这是源码确定的控件/请求路径问题，本轮未做 GUI 点击复现。应为停止提供独立的高优先级路径，允许它使普通在途操作失效，且避免迟到的普通响应覆盖停止后的界面状态。

复验：主动延迟普通操作后，实际点击停止按钮应可调用停止并呈现已停止；正常防重复点击和授权行为不退化。
