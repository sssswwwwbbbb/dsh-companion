# DSH 整套皮肤：整体思路与实施方案（评审后修订）

整理日期：2026-11-03（Asia/Shanghai）。

本轮范围是需求讨论、只读核对和文档整理。用户已同意三角色评审后的改进建议，先补齐五份设计约定，再推进底座。底座尚未开始实施，首套皮肤范围和主题尚未冻结，流程技能继续保持骨架。

配套文档：[底座设计约定 v0.1（五份设计输入）](skin-foundation-contracts-v0.1.md)、[三角色评审报告](skin-plan-review-2026-11-03.md)、[评审时方案快照](skin-plan-reviewed-baseline-2026-11-03.md)。技术协议及行为细节以设计约定为准；文档形成不表示接口已经验证或代码已经实现。

## 1. 产品定位与已确认方向

目标是让用户通过一个 DSH 插件管理和切换整套皮肤，后续开放皮肤制作能力，让其他创作者自制和上传自定义皮肤。每套皮肤具体包含哪些界面、动画、角色与互动，仍待确定。

已确认的方向：

- 一个插件入口，通过配置切换皮肤，共用一份激活码。
- **已确认的后续功能**：制作皮肤的能力要开源，其他人能够利用本项目制作自己的皮肤。
- **已确认的后续功能**：用户安装插件后，能够自制皮肤并上传自己的自定义皮肤。上传的接收位置、是否面向他人公开及配套服务仍待明确。
- Mac Apple 芯片优先验证；Windows 和其他 DSH 版本后续分别适配。
- 尽量复用已有能力和开源组件，保持轻量、简单。
- 先讨论方案，再确定首版覆盖面、主题、素材和开发任务。
- 已同意先补齐最小体验清单、模块执行位置表、切换状态表、设置与版本规则、样例验收清单；样例阶段提前检验受控官方宿主中的实际体验。
- 首轮技术验证组合已选择“主工作区主题＋现有桌宠”；这不代表对应模块已成为正式首版必选项。

建议的整体结构是：**统一入口 + 可复用的皮肤底座 + 按需接入的功能模块 + 开放的创作工具与格式 + 多作者皮肤包。**

“先做底座”的含义是先明确最小用户场景和技术验证组合，再补齐加载、切换、设置与退出的共同规则，并用少量样例证明这些规则成立。包格式和模块接口为未来外部创作保留扩展位置；开源制作工具、制作界面和自定义皮肤上传均安排在后续，不作为当前最小底座或首套皮肤的交付条件。

## 2. 参考对象各自承担什么作用

用户提到的 Wallpaper 明确指 **Steam 上的 Wallpaper Engine**。它与 `elysia395/dsh-wallpaper-engine` 是两个不同的参考对象。

Steam Wallpaper Engine 支持不同内容、用户可调参数、播放规则和性能控制。这些产品机制适合借鉴为本项目的“统一运行环境承载多套内容”。这是本项目的设计归纳，不是对其内部架构的源码结论。[官方产品介绍](https://www.wallpaperengine.io/en)、[官方 Web 壁纸创作接口](https://docs.wallpaperengine.io/en/web/overview.html)。

截至本轮查阅，未找到原版完整引擎的官方开源仓库或开源许可。已确认公开的是创作工具说明和接口；因此目前不把 Steam 原版列为可直接复用的代码底座，也不据此承诺兼容其全部项目格式。

| 参考 | 本项目主要借鉴什么 | 使用边界 |
|---|---|---|
| Steam Wallpaper Engine | 内容与运行程序分开、用户参数、效果启停与性能策略 | 产品参考；未确认完整引擎开源 |
| dsh-pixel-ui | 主界面主题、控件样式、字体及设置接入 | 核对目标 DSH 接口后再决定复用 |
| dsh-wallpaper-engine | 背景、外观组合、预设携带资源、模块共存 | 动态场景和 WE 格式兼容另行评估 |
| EAC-skin-loader | 注册、激活、停用、切换失败和资源清理 | 包格式和目标宿主不同，不能直接视为兼容 |
| dsh-boot-animation | 开场播放、跳过、超时与主界面交接 | 页面开场与本项目原生启动阶段分开处理 |
| dsh-skin-market | 列表、预览、兼容说明，以及安装与生效状态 | 市场不是最小底座的前置条件 |
| EAC-Desktop、da-feiyu-player | 宿主区域分工、音乐响应和动效制作 | 按实际需求选用；不预设更换宿主或增加播放器 |

7 个独立仓库的固定阅读版本、关键源码与许可说明见 [参考调研](skin-reference-review-2026-11-03.md)。本轮未安装或运行这些项目，所列参考价值不等于已经选用。

## 3. 用户最终会怎样使用（建议）

1. 安装并激活统一插件，进入同一个皮肤管理页面。
2. 选择已有皮肤，查看其包含的模块与兼容情况。
3. 应用后，由底座协调本套皮肤涉及的效果；状态能够说明哪些已生效、哪些不可用。
4. 用户可调整已支持的参数或关闭某个效果；换肤时保留明确的全局偏好。随时切换其他皮肤或退出换肤，恢复到约定的可用外观。

后续增加创作者流程：新建皮肤 → 填写信息及替换素材/参数 → 预览与检查 → 打包导出 → 上传或导入 → 应用。该流程已列入后续功能清单，具体界面、上传接收位置及公开范围届时明确。完整在线市场、订阅、复杂时间轴编辑与高级场景编辑器另行讨论。

## 4. 底座、模块和皮肤包的分工

| 部分 | 负责什么 | 不同皮肤之间如何复用 |
|---|---|---|
| 统一入口 | 授权、皮肤选择、参数设置、状态和恢复操作 | 用户一直使用同一个入口和授权 |
| 皮肤底座 | 宿主能力判定、包与资源管理、切换协调、配置保存、异常恢复 | 每套皮肤使用相同的加载和退出流程 |
| 功能模块 | 在具体位置呈现效果，例如界面主题、背景、启动动画或桌宠 | 模块代码随插件维护，皮肤提供它需要的资源和参数 |
| 开放创作能力（后续） | 公开格式、模板、制作入口、校验打包工具、文档及示例 | 项目维护者和其他作者使用同一套制作流程 |
| 皮肤包 | 标识、名称、作者、版本、预览、模块声明、素材、默认参数、来源与许可 | 自有和用户自制皮肤通过同一套规则加载；新增能力时再扩展模块 |

后续需求隔离的设计原则：底座只依赖统一的模块接口；皮肤通过模块标识及配置声明需求，具体字段与互动由模块解释。新增配置优先留在所属模块，新增互动优先扩展模块或宿主适配层；需要新的公共服务或协议语义时，再升级底座。详细规则见 6.7 和配套设计约定。

DSH 页面内的主题、背景等通过宿主接口接入；原生启动窗口和系统桌宠继续由现有桌面运行层承担。底座协调两边的状态，具体接口和窗口管理由各自适配层负责。

设计上由 Host 侧皮肤协调器统一提交皮肤选择及用户参数，页面和原生执行端只负责自己的效果及结果回报。现有代码仍需适配，不能将当前多个位置写设置文件的实现视作新合同已经成立。

建议首阶段让皮肤包只包含声明、参数和受支持资源，并为后续外部作者制作保留扩展位置。需要执行代码的新效果放在受控功能模块中维护。用户制作和上传本项目格式皮肤属于已确认的后续功能；第三方代码型皮肤、其他管理器协议以及 Wallpaper Engine 项目导入，均作为独立兼容需求评估。

## 6. 最小底座的建议范围

### 6.1 宿主能力与接入边界

先核对目标 DSH 的主题、插槽、启停和配置接口。交接记录的目标内核是 DSH 0.2.1-rc.5，实施前应确认实际目标版本。优先使用宿主提供的扩展能力；确需依赖页面结构的部分，集中管理并记录适配版本。

先确认界面内效果与原生窗口分别能做到什么，再确定首轮样例范围。未验证的接口不作为已支持能力展示。

### 6.2 皮肤包和资源合同

规定包标识、内容版本、格式版本、兼容条件、模块列表、资源引用、默认参数和许可记录，并预留作者等信息。皮肤资源与固定角色目录解耦，同时保留已有配置的迁移或回退路径。后续开放创作时，公开对应规范，并让内置示例与用户自制包使用同一校验规则。

首阶段建议只定义样例实际需要的格式和资源类型；模板、公开说明及面向创作者的校验打包工具在后续开放制作阶段完善。导入成功与应用成功应分别记录。资源包设计应与某个安装实例解耦，不携带制作者的激活信息、设备标识或机器绝对路径。

### 6.3 加载、切换、退出和失败恢复

设计流程：检查并准备新包 → 结束旧效果 → 应用新效果 → 等待实际就绪 → 协调器提交选择。区分用户请求、应用中状态和最后成功结果；每次操作有独立标识，迟到回报不影响后续操作。请求串行处理，必需能力在破坏当前效果前检查。

每个模块负责释放自己的样式、节点、监听器、定时器、媒体和窗口。新效果失败时先清理，确认可恢复后尝试上次成功状态；清理未知或恢复失败时进入停止效果/故障状态并提供下一步，不能报告成功或循环自动应用失败皮肤。

退出只撤销本插件持有的改动，显示宿主当前有效外观，不以旧快照覆盖其他插件后来的修改。管理页不可用时必须有独立恢复路径，具体方式仍需宿主核对和实际验证。与其他全局外观插件仅承诺经验证的共存范围，不自动停用其他插件。

### 6.4 用户设置与皮肤默认值

建议把设置分成两类：

- **全局偏好**：例如模块开关、静音和性能档位（仅对已接入模块提供）。用户明确关闭的效果，不因换肤而重新开启。
- **每套皮肤的参数**：例如颜色、背景选项、角色尺寸等，按皮肤保存；首次使用才采用包默认值。

参数按模块默认值、包默认值、用户覆写合成；用户关闭效果作为独立运行约束。只保存用户实际修改的覆写，不把包默认值写成用户偏好。必需能力缺失时阻止应用；能力存在但用户关闭效果时尊重关闭并说明。

“重置本套参数”只清除本套覆写；“退出皮肤/停止全部皮肤效果”撤销效果并保留授权、参数和停止意图。停止意图只由用户主动应用/恢复成功解除，重启或重新启用插件不解除。普通参数在应用成功后保存；关闭效果先保留关闭意图，即使清理失败也不自动重开。详细行为及迁移/回退规则见配套设计约定。

### 6.5 统一状态与授权

复用现有授权与插件入口，不增加逐皮肤重复激活流程。分别表示包已导入、当前已选择、模块已启用和效果实际生效，支持查看失败原因及恢复操作。

### 6.6 基本运行与性能规则

为实际接入的动态模块定义播放、暂停和停止规则。例如页面内效果不可见时暂停，停用后释放资源。原生桌宠有独立可见性，不能直接套用主窗口是否最小化的判断。

帧率、资源大小和多效果同时运行的预算，在确定样例与目标设备后给出。首阶段无需预先实现游戏检测、复杂调度或完整场景引擎。

### 6.7 隔离后续皮肤需求，并允许能力演进

底座应提供稳定的扩展规则，但不能预先支持所有尚未设计的互动。需区分“皮肤配置变化”“模块能力变化”和“底座公共能力变化”，避免每增加一个皮肤字段都改动核心，也避免将任意新配置误当作旧版本已经支持的新功能。

| 后续变化 | 主要修改位置 | 底座核心是否需要修改 |
|---|---|---|
| 替换角色、背景或已有动作素材 | 皮肤包资源与配置 | 已支持对应资源类型时不需要 |
| 为已有能力选择不同数值，例如已支持的动作间隔、大小 | 皮肤包参数 | 不需要；参数必须在当前模块支持范围内 |
| 增加一个参数，例如新增点击反应次数或拖拽回弹强度 | 对应模块的配置定义、校验、行为实现，必要时增加迁移 | 通常不需要；旧模块不会仅凭新增字段自动获得行为 |
| 组合已支持的事件与动作，形成新的互动规则 | 皮肤包中的声明式规则，由已支持该规则的模块解释 | 已有事件、动作和组合语义足够时不需要 |
| 新增事件来源、渲染方式或互动能力 | 新模块，或现有模块及宿主适配层 | 现有公共接口足够时不需要；目标宿主必须实际提供所需能力 |
| 需要新的跨模块协调规则、运行权限或资源/窗口服务 | 底座接口及相关适配、模块 | 可能需要，必须设计兼容与升级路径 |

首阶段保留以下边界，具体接入协议在实施前结合接口核对和样例确定：

1. **模块自己的配置由模块负责。** 按模块标识分区保存参数；模块声明字段类型、默认值、范围、校验和配置版本。底座负责登记、路由和持久化，不集中判断每个角色或互动字段。未来制作工具可根据模块的字段描述生成常见输入项；特殊编辑器由对应模块扩展。
2. **模块使用共同的生命周期。** 模块至少有准备、应用、更新配置和退出的约定，并记录自己持有的资源。皮肤切换由底座协调，模块负责执行及清理；一个皮肤不能直接修改另一个模块的内部状态。
3. **事件与动作通过明确接口连接。** 支持的事件来源、可用动作和参数需要声明；例如“工作完成后播放动作”只有在目标 DSH 事件已验证、相应动作模块存在时才成立。新来源先接入适配层或模块，不能在包中写一个事件名称就假定宿主支持。自定义互动仍通过受支持的声明式规则或模块实现，资源包不携带任意执行代码。
4. **包格式、模块接口与模块配置分别演进。** 包声明所需模块及兼容条件；新增可选字段有默认值，旧配置升级由所属模块迁移。存量包不强制同步重制；无法迁移或不兼容时给出可理解的结果，并保留原配置以便恢复。读取未知配置时不执行，也不在往返导出或保存时静默丢弃；具体保留规则纳入配置合同。
5. **缺少能力有明确处理。** 对必须模块或最低版本不满足的包，在改变当前皮肤前阻止应用并提示升级；对明确声明可选的模块，可跳过并说明缺少的效果。未知能力不能一律忽略后仍显示整套应用成功。

不改底座核心代码，不等于用户永远无需升级插件。首版模块可以随插件一起打包，新模块发布时用户可能仍需升级整个插件；独立下载模块和热加载机制不作为首阶段要求。

首阶段只需用选定模块验证接口和配置分区确实成立。后续若一次新增互动迫使授权、皮肤列表、配置存储和全部渲染层同时改动，应检查职责是否混在一起。底座需要升级时，优先新增可复用公共能力，避免写某套角色专用的分支。

| 制作皮肤的能力开源 | 已确认，后续实现 | 具体开源包、代码范围和许可证待定 |
| 安装插件后可制作自定义皮肤 | 已确认，后续实现 | 制作入口及编辑能力届时设计 |
| 上传自己的自定义皮肤 | 已确认，后续实现 | 接收位置、公开范围及配套服务待定 |

底座当前只需保留版本化包格式与模块扩展位置。后续创作能力应让外部作者能够读懂规范、独立制作、检查和交付内容。

建议将制作所需的格式说明、模板/示例、基础制作工具、校验与打包工具、必要的加载和模块接口作为开源交付的一部分。具体开源包的拆分及许可证尚未确定；本补充不自动决定授权服务或全部项目代码的开源范围。

建议提供两条共用格式的制作路径：

- **插件内基础制作**：选择模板，为已支持模块填写信息、替换素材和调整参数，预览并检查，再保存或导出。具体支持哪些模块，仍随首阶段范围确定。
- **开源模板与工具**：创作者可直接编辑项目文件，使用公开工具完成校验、打包，并通过插件导入预览和使用。

首套正式皮肤制作时记录可复用步骤；后续开放创作时，将适合公开的部分整理为示例并验证同一流程可用。开源示例使用可随项目分发的素材；其他作者的作品分别记录作者与素材许可。

建议加入这些共同规则：

- 创作草稿、临时预览和已应用皮肤分开管理；退出预览能够清理效果，未经应用不覆盖当前选择。
- 包格式有版本和升级说明；作者、皮肤标识与内容版本可区分，不因同名覆盖其他人的作品。
- 缺失资源、参数错误和不兼容模块应定位到具体问题，创作者能够自行修正。
- 用户自制包与内置包使用同一加载和清理流程，包内资源检查不依赖作者机器。
- 制作、导出和上传的包不包含激活码、密钥等安装实例信息。

“上传自定义皮肤”已是需求，但仍需明确接收位置及公开范围：上传到当前插件供本人使用、上传到个人空间，或发布到公共皮肤库供他人下载。现阶段不将其中任一种单独视为已选方案；服务端存储、登录、发布状态和版本管理应依据该选择再设计。

## 8. 评审后的推进顺序与每一步的结束线

| 阶段 | 做什么 | 结束线 |
|---|---|---|
| 当前：评审后设计约定 | 整理五份设计输入，区分已选技术组合、正式范围和未验证能力 | 已形成配套设计文档，组合已选；正式模块、主题及接口未视为冻结 |
| 第一步：场景收敛、能力验证与合同定型 | 明确最小场景及元素，核对目标宿主和恢复路径，定型模块/配置/资源/切换合同 | 关键接口有证据；最小组合和预算有明确验证条件 |
| 第二步：最小底座与两套样例 | 用具有模块差异的 A/B 内容贯通切换，覆盖配置扩展和失败，并提前检验受控官方宿主体验 | A → B → A → 退出可往返；旧效果清理；设置保留；日常操作和异常恢复有实际证据 |
| 第三步：首套正式皮肤 | 确认覆盖面、角色主题和重要互动；补齐所需模块与素材 | 风格与功能达到约定，记录可复用的制作步骤 |
| 第四步：实机验收与交付 | Mac ARM、约定 DSH 版本下验证使用流程；整理分发材料 | 分别记录实现、检查、打包分发和真实客户端验收证据 |
| 后续已确认：开放制作与自定义上传 | 开源制作能力，贯通制作、预览、校验、打包及自定义上传；依据明确的上传位置实现对应流程 | 其他人能按文档独立制作并使用皮肤；开源工具与示例可复现 |
| 其他候选扩展 | 更多主题、Windows、其他版本、外部格式、完整市场或高级编辑器 | 每项单独评估收益、适配和验收成本 |

两套技术样例不需要正式美术。用户已选择主工作区主题与现有桌宠作为首轮技术组合；配套设计中 A 只使用主题，B 使用主题与现有桌宠，以验证模块组合差异，并增加受控异常变体。具体覆盖元素仍需收敛，不能推定对应功能必须进入正式首版。

最小底座的共同验收建议：

- 两套包能连续切换并退出；已选模块产生的样式、媒体、窗口和任务按归属清理。
- 用户明确关闭的模块不会被换肤重新打开；重启后选择和设置符合约定。
- 缺失资源、不兼容版本和应用失败都有明确结果，并能回到可用状态。
- 已有授权和应保留的数据不因换肤受损；原插件启停链路按约定工作。
- 所选模块的资源消耗达到事先约定的预算。
- 对已选模块，皮肤素材及受支持参数的变化只修改包内容；模块配置互不覆盖，旧配置按约定继续可用，缺少必需能力时不破坏当前皮肤。
- 样例阶段已有受控官方宿主的实际体验证据；所选区域可读、可输入及滚动；页面不可用时的备用恢复经过实际验证。

完整样例及阶段验收条目见 [底座设计约定 v0.1](skin-foundation-contracts-v0.1.md)。本轮只完成文档，这些检查尚未执行。

后续开放制作阶段的额外验收：创作者能用公开模板制作并导出皮肤，资源随包携带，另一份兼容安装能导入使用；由未参与实现的人按文档完成一次“制作 → 预览 → 校验 → 导出 → 上传/导入 → 应用”，用实际操作验证他人是否能够独立使用。这些不列入当前底座验收。

## 9. 首套皮肤仍待确定的事项

以下均为候选，暂未标为首版、后续或不做：

| 候选模块 | 入选后需要明确的边界 |
|---|---|
| DSH 主界面 | 侧栏、会话、聊天、输入框，以及设置、菜单和弹层覆盖多少 |
| 背景与氛围 | 静态或动态、应用区域、玻璃或粒子等效果是否需要 |
| 字体、图标和角色元素 | 替换哪些元素，保留哪些含义与可读性 |
| 启动与过渡 | 覆盖哪个启动阶段、时长、跳过和交接方式 |
| 桌宠 | 是否包含、角色动作、现有互动保留范围 |
| 声音 | 是否包含，触发事件、音量与静音规则 |
| 新增互动 | 是否需要随 DSH 工作状态变化；优先验证哪 1～2 个体验 |

角色、世界观、视觉感觉、素材来源和使用/分发范围同样未定。提供参考仓库不代表选用其角色、素材或所有功能。

首次范围、主题、功能取舍问题按用户要求暂缓。现已完成参考阅读和三角色评审，用户同意补齐设计约定；下一步收敛技术验证场景和元素，再带着已验证能力确定正式皮肤范围与主题。
