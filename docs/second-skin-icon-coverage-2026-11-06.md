## 已排除的原因

1. **素材缺失**：不存在。包内 50 对图标（浅/深各一）齐全，制作工具包校验 `valid`，ZIP 内可逐项对上。
2. **路径写错**：替换表里 160 条 `d` 路径中，159 条确实存在于当前 DSH 前端的图标定义里，路径本身没有过期。
3. **CSS 没生效**：生效了。同一张皮肤表里唯一一条类选择器（`svg._folder_1wejo_16`）命中了，发送/停止的路径选择器也命中了，说明 `body.dsh-workspace-commander` 类与注入的 `<style>` 都在。

## 推断

命中的两处都不是「侧栏/头部那套图标」：

- 发送/停止属于输入区；
- `_folder_1wejo_16` 是**文件类型图标**（同一组里还有 code / excel / html / image / markdown / pdf / ppt / video / word），出现在工作区树的行首。

而侧栏导航与工作区头部用的是另一组图标实现，它们的 `d` 或渲染结构不在替换表的 160 条路径里，所以 `svg:has(path[d="…"])` 没有命中。也就是说：**替换表覆盖的是文件/输入区那套图标，没有覆盖侧栏与头部那套**。

## 建议（供引擎侧参考）

1. 在 `0.2.2-rc.1` 的实机上抓一次真实 DOM，重新生成 leaves 表；现有表注释写的是 `rc.5 leaves`。
2. 侧栏与头部优先用**类选择器或 data 属性**定位（如 `_folder_1wejo_16` 这种 CSS Module 类名在同一构建内稳定），比逐条比对 `d` 路径更抗改版。
3. 若短期不改引擎，可以在交付说明里标注「语义图标当前仅覆盖输入区与文件类型图标」，避免作者误以为 50 个位都生效。

## 复现

1. 应用 `duelist-sky-dragon` 0.1.1。
2. 观察侧栏「插件 / 自动化任务 / 更多」与「工作区」头部三个图标：仍为原生色。
3. 观察工作区树里的文件夹行：文件夹图标为皮肤红色。

### 与 dev.35 对比

结论没变，命中集合还是一条：**类选择器命中，路径选择器不命中**。dev.46 的替换表仍是 228 条选择器、其中 13 条非路径选择器（对应上面 7 个键 + html/other 等文件类型），路径占比 94%，实际零命中。

### 给引擎侧的建议（沿用上次）

1. 侧栏与头部改用类选择器或 `data-*` 属性定位，不要逐条比对 `d` 路径。
2. 若短期不改，交付说明里继续标注「语义图标当前仅覆盖输入区与文件类型图标」，避免作者误以为 50 位全生效。
3. 可考虑让宿主把图标直接渲染成 `<img>` 或 mask，作者就只需交单色形状，不必为不同底色出两套。
